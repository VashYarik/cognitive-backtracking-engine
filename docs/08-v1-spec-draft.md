# CBE Version 1 Spec (FROZEN v1.7, 2026-11-13)
Status: FROZEN. Every section was reviewed with Yarik one decision at a time. Changes from here on are made deliberately and logged in section 11. PRECEDENCE: where this spec disagrees with docs 00 to 07, this spec wins; those docs remain as the history and reasoning behind each decision. Numbers marked (placeholder) are starting values to calibrate in Phase 1.
(The file name still says "draft" so existing links keep working.)

## 1. Purpose
Root: erase cognitive friction through real-time structural error-correction. In v1: during a lecture, detect when a meaningful part of the class has lost the thread, and give the professor the whole concept tree so they can choose where to go back to and re-anchor the class.
Scope: classes of about 30, students on phones and laptops, a small pilot (3-10 professors in the first semester), solo build, no fixed date. Stack: Node.js + TypeScript back end, PostgreSQL, React front end.

## 2. Users
- Professor: has an account. Builds and approves the concept tree, runs pulses, sees one live number and the concept tree after an alert.
- Student: no account. Joins by QR code or short code, once per class, and keeps the page open. Anonymous.

## 3. Before class
1. The professor gives the course material. An LLM proposes a concept tree: concepts, prerequisite links, one root (Node 0). The format of the course material is left to design (D16).
2. The professor edits and approves it. A validator must pass first: no loops, exactly one root, every concept leads back to the root, exactly one goal (3.6, v1.6), every lecture segment is tied to a concept. If the check fails, the system names the check that failed (D21). Lecture segments stay in v1: the professor defines them and ties each to a concept (D17).
3. The professor marks each concept ordinary or critical. A concept left unmarked is treated as ordinary (D18). The system pre-suggests critical for each concept that at least 3 other concepts depend on, counting both direct dependents and dependents through prerequisites (3 is a placeholder) (D19).
4. The professor sets the current concept only from an approved concept tree (D20).
5. The professor can declare which concepts each lecture covers. The declaration is kept, but nothing in v1 reads it; it is reserved for the parked lecture-only view (D22).
6. The professor marks exactly one concept as the goal: the concept the course builds towards (v1.6). The goal's scope is the goal and every concept it builds on (its prerequisites, their prerequisites, and so on, down to the root). The tree holds the full course material: concepts outside the goal's scope stay in the tree with all their links. The professor can move the goal to another concept outside a session, for example when the course is cut short or extended; moving it is an edit to the tree, so the tree must be approved again. 4.15 limits a session to the goal's scope.
Links between concepts carry no explanation text.

## 4. During class
1. Students join once; the page stays open on a calm ambient screen. No sound, no vibration, no countdown.
2. The professor sets the current concept ("the concept the pulse is about"), chosen from the goal's scope (4.15, v1.6), and says "quick check" out loud at a natural breakpoint (ideally after a short pause or example), then fires a pulse.
3. Pulse P1 (quick gut answer): "Could you explain the last idea to a classmate right now?" Buttons: "Yes, I could" / "Not yet". Skippable by not answering; there is no skip button (v1.7). P1 wording is the starting version; a bank of equivalent wordings will be built, and each pulse stores which wording it used.
4. Pulse P2 (considered rating), asked of EVERY student right after P1: they rate 1-7 how well they could explain the concept to a classmate (1 = "I can't follow any of it", 7 = "I could explain it to a classmate"). The control is a slider (REVISED 2026-10-25, was seven tap buttons) over whole numbers 1 to 7, only the ends labeled. Skippable by not answering; there is no skip button (v1.7). P2 appears as soon as the student answers P1; if P1 is not answered within 8 seconds (placeholder; shorter than the answer window), the screen moves on to P2 without a countdown and that student's P1 stays empty (v1.7). Nothing about this switch is recorded. Everyone sees the same follow-up, so the screen looks the same whatever a student answered. Where the slider starts, and how an untouched slider is told apart from an answer, are OPEN (section 9); until settled, no rating is counted unless the student has moved the slider.
5. Answer window covers both taps: default 25 seconds (placeholder; Yarik said 20-30), professor can set 15-60. It closes early when every student who had joined when the pulse fired has given a P2 rating (v1.7), or when the professor closes it; otherwise it closes when the window ends. No countdown. A late tap gets a quiet "That check has finished, thanks."
6. The professor sees ONE live number: "Following: 18 of 24 (75%)", where following = rated above the lost cutoff; count shown next to the percentage because each student moves it by about 4 points. The server sends the number at a fixed interval of 5 seconds (placeholder; REVISED 2026-11-12, v1.5), not after each rating, so that a single change in the number cannot be tied to a single student's answer. It first appears at the first send after at least 3 ratings (placeholder; REVISED 2026-11-11, v1.4, was 5) are in (REVISED 2026-11-04, D23: the fixed delay of about 7 seconds is removed; the wait for the next send is at most one interval); before that, nothing is shown for the live number (D27). It updates at each send until close; when the pulse closes, the final summary is sent at once. The interval is a stored value in the database, not a professor setting, and no professor screen edits it in v1. Groups under 3 are never shown. The P1 tap is recorded but not displayed. The "said Yes but rated low" mismatch is recorded for analysis, not displayed. A student's two answers are used together only within that one pulse, and the professor's screen never receives the link between them (see section 5 for how the server stores it).
7. Fracture rule (rating only): confirmed when at least 25% (placeholder) of the students who gave a rating rated at or below the lost cutoff, and at least 3 students (placeholder; REVISED 2026-11-11, v1.4, was 5). The 25% is the alert bar: the share of rating students at or below the cutoff, which the professor can adjust (D1). The 3-student minimum is the same single value used in 4.6 and section 5 (v1.4); it is a placeholder and is not a professor setting. It is a stored value in the database, and no professor screen edits it in v1. Equivalent to the number in step 6 being 75% or lower. Cutoff: 1-3 for an ordinary concept, 1-5 for a critical one (the concept is the one the pulse was about). The P1 tap is not used for the alert. The rule is checked at each send of the live number (4.6) and once more when the pulse closes, not after each rating (v1.5).
8. The professor can adjust the lost cutoff and the alert bar. The displayed number and the alert always use the same settings and are worked out at the same moment, so they can never disagree. A free-form formula builder is NOT in v1.
9. When a fracture is confirmed (REVISED 2026-10-19), the professor gets a quiet alert and can open the concept tree. The tree is shown whole. The system highlights nothing: no lost concept, no ancestors, no suggested path or starting point. The only markers are a quiet "you are here" on the concept the pulse was about and a quiet "goal" marker on the goal concept (3.6; added in v1.6), both for orientation. The professor chooses where to go back to, among the concepts in the goal's scope (4.15) (the system never decides where the class got lost, and the trouble may have started before the current concept), says it aloud, and taps "We walked back to [concept]". That confirmation, and only that, counts as a walk-back: it records the concept and the time. Opening the tree without confirming is not a walk-back.
   Two concepts are kept apart: (a) the concept the pulse was about (set before firing; decides the lost cutoff) and (b) the concept walked back to (chosen and confirmed after the alert; used by 4.13 and the acted-on rate).
10. After a walk-back, the professor can re-ask right away: another pulse with the same questions about the concept the pulse was about (D3, 2026-11-04). In Limits mode the minimum gap between pulses still applies, with override allowed.
11. Cadence: at least one baseline pulse per lecture. The lecture clock starts when the first student joins (D5); if no pulse has been fired 20 minutes (placeholder) after that, the system reminds the professor. Second pulse mode, set by the professor: Nudge (default; at a fixed 20 minutes (placeholder) after the first pulse of the lecture the professor sees a prompt they can fire, snooze up to twice, or ignore; the system never fires by itself) (D6) / Automatic (professor opts in; fires the second pulse at the same time the Nudge prompt would appear, unless a pulse is open at that moment) (D7) / Off (no prompt, no second pulse). Limits mode, set by the professor: Guidance (default; nothing blocked; one gentle hint when the last pulse was less than 10 minutes ago (placeholder)) (D8) / Limits (at most 4 pulses, at least 15 minutes apart, override allowed; placeholders).
12. Optional professor setting, OFF by default: after a pulse closes, show students one neutral thank-you line, the same whatever the result (D9; this replaces the earlier example "Most of us are with you; a few are not yet", which changed with the result). Never shown while students are still answering.
13. Near the end of class, the professor triggers one skippable tap for every student who has joined and has the page open at that moment (D10): "Earlier we went back to [concept]. How useful was that for you?", where [concept] is the confirmed walk-back concept (4.9b). 1 = "a waste of time for me", 7 = "it really helped me". At most the last two confirmed walk-backs. If no walk-back was confirmed in the lecture, the professor is told there is nothing to ask about (D11). The rating control is left to design (D12).
14. After quizzes or exams, the professor can enter class-level results per concept (percent correct). No individual scores.
15. Goal scope in a session (v1.6): during a session, only concepts in the goal's scope (3.6) can be the current concept, the concept a pulse is about, or the concept walked back to. Concepts past the goal stay in the tree but cannot be used in a session, so the goal is always the last concept a course can reach. Going back to earlier concepts in the scope is always allowed. To go further, the professor moves the goal outside a session (3.6).

## 5. Privacy and safety rules (hard rules)
- The professor can never tell which student answered what. Totals only. Where a result would otherwise be shown for a group under 3 (placeholder; REVISED 2026-11-11, v1.4, was 5), the screen shows "Not enough responses" instead (D27). Enforced on the SERVER: the professor's screen never receives individual answers.
- Each student has a random code valid for one session only, used to route the end-of-class tap and to link a student's two answers within one pulse. The server stores the code on each of that student's answer rows until the code is discarded (v1.4 clarification), which also stops the same student answering one pulse twice. The link is never sent to the professor's screen. The code is discarded automatically 2 hours (placeholder) after the first student joins (D24), or when the session ends, whichever comes first. No cross-session tracking, no student accounts, no per-student export.
- Response time is not recorded. This includes the time an alert is raised: it is the time of a send of the live number (4.6) or of the pulse closing, never the time of one student's answer (v1.5).
- Pulses are skippable; "Not yet" is framed as a normal, useful answer.
- Students are told, in plain words, what the professor can and cannot see. The privacy notice is shown once, when the student joins, and says only that the professor sees only totals and never which student gave which answer; it does not include the "Not yet is a normal answer" sentence (D25).
- A professor's data (class results, walk-back use, acted-on rate) is private to that professor by default. No department head, administrator or institution can see it. There is no sharing feature in v1; sharing a professor's data on the professor's choice is a possible future feature, not part of v1 (D26). In the pilot, class-level data is used for research only with the professor's agreement.

## 6. Not in v1
Student accounts; response timing; any system-suggested walk-back start; highlighting of a lost concept, ancestors or any walk-back path on the tree; the live recovery check question (P3) and the re-anchor prompt text; explanations on concept links; the hidden calibration sample for "Yes" answers; displaying the P1 counts or the Yes-but-rated-low mismatch; a free-form formula builder for the live number; microphone listening; any per-student data; a feature for a professor to share their data with others; the controlled 3-arm trial (Phase 2).

## 7. How we will know it works (Phase 1, observational)
Acted-on rate (share of alerts followed by a confirmed walk-back); response rate per pulse (a falling rate warns of unrepresentative answers); fracture confirmation rate per lecture and whether professors agree it was real; whether the second question (P2) tells us anything the first tap (P1) does not, including how often "Yes" students rate themselves low (if not, drop to one question); end-of-class usefulness ratings; class-level quiz results on concepts with and without a walk-back (not causal on its own; regression to the mean); whether professors link concepts aloud under time pressure; how professors use the tree (how long it is open, which concepts they choose to go back to, how far back from the concept the pulse was about).

## 10. What this spec supersedes
- 05: C4 ("genuinely lost" = Not yet AND low rating; P2 only for Not yet students) is replaced by the rating-only rule in 4.7; the 20-second window in 07 (G21) is replaced by 25 seconds covering both taps. C1 ("lost concept marked, all ancestors highlighted back to Node 0; default lecture view with earlier ancestors dimmed") is replaced by 4.9 (2026-10-19): the professor chooses where to go back to and confirms it; nothing is highlighted. The part of C1 that stays: the professor decides where to start, and the system makes no suggestion.

- 04: all earlier research proposals not repeated here, including temporal bracketing, the re-anchor prompt, P3 and latency baselines.
- Any earlier mention in docs 00 to 07 of P2 as seven tap buttons: the control is a slider (4.4, 2026-10-25).
- Any earlier mention in docs 00 to 07 of a delay before the live number appears, of a "random window" for the second pulse, of a student summary line that changes with the result, or of professor data being shared on the professor's choice (v1.3, 2026-11-04: see 4.6, 4.11, 4.12 and section 5).

- Any earlier statement in this spec before v1.5, or in docs 00 to 09, that the live number updates after each rating, appears at the moment the minimum is reached, or that the fracture rule is checked after each rating (v1.5, 2026-11-12: see 4.6 and 4.7).
- Any earlier statement in this spec before v1.6, or in docs 00 to 09, that "you are here" is the only marker on the tree, or that a session may use any concept of the tree (v1.6, 2026-11-13: see 3.6, 4.9 and 4.15).
- Any earlier mention of a skip button or a skip action, or of P2 being reachable only after P1 is answered (v1.7, 2026-11-13: see 4.3 to 4.5).
